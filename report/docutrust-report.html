1 Problem Statement

What security problem is being addressed?

A PDF document carries no inherent evidence of its own authenticity. Any person who obtains a contract, offer letter or certificate can open it in an editor, change a figure, and redistribute it. The altered file opens normally in every reader and is visually indistinguishable from the original — appearing genuine is the entire objective of a forgery.

Conventional safeguards do not solve this. Email headers can be spoofed, a scanned handwritten signature is simply an image that can be copied, and a password only restricts who may open a file rather than proving what it contains.

Why is it important?

  • Financial exposure. A single altered digit in a salary, invoice or loan amount has direct monetary consequence.
  • Legal admissibility. Electronic records must be shown to be unaltered before they carry evidentiary weight.
  • Repudiation. Without cryptographic binding a signatory can credibly deny having approved a document.
  • Scale. Organisations exchange documents in volumes that make manual verification impossible.

What are the real-world applications?

Employment contracts, financial statements, academic transcripts, medical records, government notifications, tender documents and software release notes — any artefact whose integrity and origin must be demonstrable to a third party.

The core question this project answers: given only a PDF file and nothing else, can a receiver prove that its contents have not changed since a specific, identified party approved them?

2 Objectives

#ObjectiveDescription and success criterion
1Apply genuine digital signatures Embed a standards-conformant PAdES Baseline-B signature inside the PDF itself, so the signed file is verifiable by any conformant validator and not only by this system. Criterion: the signed PDF carries a CMS SignedData structure with a valid /ByteRange.
2Detect post-signature modification Prove alteration cryptographically by recomputing the digest over the protected byte range rather than by comparison against a stored copy. Criterion: a single-character edit to a signed document is reported as tampering.
3Evaluate signer identity and trust Parse the X.509 certificate, validate its period and key usage, and build a certification path to an externally configured trust anchor. Criterion: a self-signed signer is reported as untrusted, not as valid.
4Report uncertainty honestly Where a property cannot be established, state that explicitly instead of defaulting to a passing status. Criterion: with no timestamp authority configured, timestamp status reads NOT_AVAILABLE and never VALID.

3 Cryptographic Concept

Algorithm / Protocol SHA-256 (FIPS 180-4) · RSA-2048 signature, SHA256withRSA (PKCS #1 v1.5) · CMS SignedData (RFC 5652) · PAdES Baseline-B (ETSI EN 319 142) · X.509 v3 certificates with PKIX path validation (RFC 5280)
Type Asymmetric (RSA — signature generation and verification) combined with Hash (SHA-256 — message digest). No symmetric encryption is used, because the objective is authenticity rather than secrecy.
Key / Parameters RSA modulus n = 2048 bits; public exponent e = 65537; digest SHA-256 (256-bit output); three-tier certificate hierarchy (Root CA → Issuing CA → Signer); key material held in a PKCS #12 keystore; ECDSA P-256 also supported.
Security Properties Integrity — any change to protected bytes is detected.
Authentication — the signature identifies the certificate, and hence the signer.
Non-repudiation — the nonRepudiation key usage is asserted; the signer cannot plausibly deny an act only their private key could perform.
Confidentiality — deliberately NOT provided. A signed document remains fully readable. Signing and encryption solve different problems, and conflating them is a common misconception.

Why hashing alone is insufficient

A digest proves a file is unchanged only relative to a digest already known to be trustworthy. An adversary able to alter the document can normally alter a published digest alongside it and recompute it to match, because computing SHA-256 requires no secret. A signature introduces a value that only one party can produce.

Verification pipeline

A submitted PDF is decomposed and subjected to six checks which are evaluated and reported independently. This separation is a deliberate design decision: a tampered document typically exhibits a failed integrity check together with a perfectly valid certificate, and reporting the certificate as invalid in that situation would be both incorrect and actively misleading.

Signed PDF
    |
    +--> Signature parser (extract /ByteRange and CMS structure)
         |
         +--> 1. Document integrity   digest recomputed over signed bytes
         +--> 2. Signature validity   CMS verified with signer's public key
         +--> 3. Certificate status   validity period, key usage, parsing
         +--> 4. Certificate chain    PKIX path to a configured trust anchor
         +--> 5. Revocation status    OCSP / CRL  (reports NOT_CHECKED)
         +--> 6. Timestamp status     RFC 3161    (reports NOT_AVAILABLE)
                    |
                    v
            Verdict composition  -->  Verification Report

Three-state verdict model

VALID
Signature verifies, content unchanged, chain reaches a configured trust anchor.
VALID_UNTRUSTED
Cryptography is sound and content is unchanged, but the signer chains to no trusted authority.
TAMPERED / INVALID
Protected content changed, or the signature fails verification.

The intermediate state exists because a well-formed self-signed signature is mathematically flawless while proving no identity whatsoever. Classifying it as valid would mislead; classifying it as invalid would be factually wrong.

Step 1 — Requirement analysis and threat modelling

A STRIDE analysis was performed before implementation, enumerating spoofing, tampering, repudiation, information disclosure, denial of service and elevation of privilege. Each identified threat was paired with a mitigation and, critically, with the residual risk that remains after that mitigation.

Step 2 — Key and certificate generation

A three-tier PKI is generated using Bouncy Castle. RSA key pairs are produced from SecureRandom. The Root CA is self-signed; it issues an Issuing CA, which in turn issues the end-entity signer certificate with digitalSignature and nonRepudiation key usage and the RFC 9336 document-signing extended key usage. Certificate serial numbers are 160-bit random values rather than a counter, so issuance volume is not leaked and independent generators cannot collide.

Step 3 — Hashing and signature application

The uploaded PDF is validated by magic bytes and a structural parse, then digested with SHA-256 using a streaming implementation. Signing performs a PDF incremental update: a signature dictionary is appended with a reserved /Contents region, and a /ByteRange declaring the two spans of the file that surround it. The digest is computed over those spans, signed, and the resulting CMS structure written into the reserved gap.

Step 4 — Verification and classification

Verification recomputes the digest over the declared byte range and compares it with the messageDigest attribute sealed inside the signature, then verifies the signature itself against the signer's public key. Findings are classified and explicitly labelled as either cryptographically proven or best-effort structural observation.

Step 5 — Adversarial testing

Twelve attack scenarios construct genuinely hostile artefacts and submit them through the same code path used by the production interface. No result is asserted that the engine does not actually produce.

8 Implementation

Implementation approach

The system is built as a modular monolith: a single deployable process partitioned into feature modules, each with its own api, application, domain and infrastructure layers. Microservices were rejected because the dominant engineering risk is cryptographic correctness rather than horizontal scale, and distribution would place network failures on the signing path without making any of that correctness easier to achieve.

Key generation

KeyPairGenerator generator = KeyPairGenerator.getInstance("RSA", "BC");
generator.initialize(2048, secureRandom);          // SecureRandom, never java.util.Random
KeyPair keys = generator.generateKeyPair();

// Certificate serial: 160 bits of randomness, forced positive.
// A counter would leak issuance volume and collide across generators.
BigInteger serial = new BigInteger(160, secureRandom).abs().add(BigInteger.ONE);

Signing process

PDSignature signature = new PDSignature();
signature.setFilter(PDSignature.FILTER_ADOBE_PPKLITE);
signature.setSubFilter(PDSignature.SUBFILTER_ETSI_CADES_DETACHED);   // PAdES

options.setPreferredSignatureSize(16384);      // reserve space for the CMS
document.addSignature(signature, options);

// Prepare the incremental update; everything except the reserved
// /Contents gap becomes the signed byte range.
ExternalSigningSupport externalSigning =
        document.saveIncrementalForExternalSigning(output);

byte[] contentToSign = externalSigning.getContent().readAllBytes();
byte[] cms = provider.sign(new SignRequest(contentToSign, "SHA-256", now, ...));
externalSigning.setSignature(cms);             // written into the gap only

Verification process

byte[] signedContent = signature.getSignedContent(pdfBytes);  // per /ByteRange
byte[] cmsBytes      = signature.getContents(pdfBytes);

CMSSignedData cms = new CMSSignedData(
        new CMSProcessableByteArray(signedContent), cmsBytes);

try {
    // Verified against the certificate's PUBLIC KEY, not the certificate
    // object: Bouncy Castle's certificate-based verifier also rejects a
    // signature whose claimed time falls outside the validity window,
    // which would conflate "broken signature" with "expired certificate".
    verified = signerInformation.verify(
            new JcaSimpleSignerInfoVerifierBuilder()
                    .setProvider("BC")
                    .build(signerCertificate.getPublicKey()));

} catch (CMSSignerDigestMismatchException e) {
    // The digest over the signed range does not match the digest sealed
    // in the signed attributes: cryptographic proof of modification.
    digestMismatch = true;
}

Hash-chained audit log

Each audit record contains the hash of its predecessor, so any retroactive edit, insertion or deletion breaks every subsequent link:

h(0) = 0…0  (genesis)
h(i) = SHA-256( h(i-1) ‖ canonical(record i) )

The canonical form is length-prefixed — each field encoded as <byteLength>:<value>; — rather than separator-joined. With a plain separator the field pairs ("alice","extra") and ("aliceextra","") serialise identically and therefore hash identically, allowing an adversary who controls part of one field to shift a boundary and rewrite a record while preserving its hash.

Verdict     : TAMPERED
Headline    : Tampering detected
Integrity   : MODIFIED

The critical observation. The substitution preserves file length, so every byte offset remains valid and the tampered file is still a structurally well-formed PDF that opens normally in any reader. It fails verification solely because the bytes covered by the signature are no longer the bytes that were signed. Note further that the certificate and its chain remain VALID and TRUSTED — reporting them as invalid would direct an investigator toward the signer's credentials when the actual fault is an edited document.

Byte range interpretation

The value [0, 1610, 34380, 779] states that the signature protects bytes 0–1609 and bytes 34380–35158. The intervening region holds the signature itself and is necessarily excluded, since a signature cannot cover its own value. Total protected content is 2389 bytes of a 35159-byte file; the remainder is the CMS structure.

Insights from results

  • Detection is size-independent. SHA-256 produces a fixed 256-bit output for any input, so verification cost is dominated by one RSA operation and does not scale with document length.
  • Signature overhead is constant, not proportional. The CMS structure grows with the certificate chain, not with the document — so relative overhead falls sharply as document size increases.
  • A length-preserving edit is undetectable by inspection but trivially detected cryptographically. This is the central empirical finding of the project.
  • Independent reporting has diagnostic value. Scenario 7 (wrong key) produced signature = INVALID with integrity = INTACT, correctly distinguishing an impersonation attempt from a content edit — a distinction a single boolean verdict would destroy.

11 Security Analysis

Security properties achieved

PropertyStatusMechanism and evidence
ConfidentialityNot provided
(by design)		 Signed documents remain readable. The objective is authenticity, not secrecy; a contract that could not be read would be useless. Transport confidentiality is TLS's responsibility.
IntegrityAchieved SHA-256 digest over the signature's byte range, compared against the sealed messageDigest attribute. Verified by scenarios 2 and 10.
AuthenticationAchieved CMS signature verified against the public key of the embedded X.509 certificate; signingCertificateV2 binds the signature to one specific certificate.
Non-repudiationPartial nonRepudiation key usage asserted and all actions audited. Weakened by file-based key storage and the absence of a trusted timestamp — stated candidly below.
Key managementDevelopment grade PKCS #12 keystore with externalised password; SigningProvider abstraction never exposes a PrivateKey, so HSM and KMS backends remain implementable.

Threats considered (STRIDE)

CategoryThreatMitigation implemented
SpoofingAdversary forges a document with a self-made certificate Trust derived only from externally configured anchors; embedded chains treated as unverified claims. Result is amber, never green.
TamperingSigned PDF is edited after signing Digest over /ByteRange; mismatch is mathematical proof of alteration.
RepudiationSigner denies having signed Certificate-bound identity plus hash-chained audit log recording actor and time.
Information disclosureOne user reads another's documents Ownership-scoped queries; "not found" and "not yours" return an identical error so identifiers cannot be enumerated.
Denial of serviceOversized uploads or unbounded signing requests Upload size limits at two layers, streaming hash computation, and token-bucket rate limiting keyed per address and per account.
Elevation of privilegeOrdinary user performs administrative action Role-based access control enforced server-side, verified by 12 tests that attempt the escalation rather than assert the configuration.

Limitations — stated explicitly

A security tool that overstates its guarantees is more dangerous than one that does less, because users calibrate their trust to the claim rather than the reality.
  • Time of signing cannot be proven. No RFC 3161 timestamp authority is integrated. The signer's claimed signing time is an unverified assertion, and the interface reports timestamp status as NOT_AVAILABLE rather than implying otherwise.
  • Revocation is not checked. The RevocationService interface exists, but only a disabled implementation is provided. Status reports NOT_CHECKED — never GOOD.
  • The audit log is tamper-evident, not tamper-proof. An adversary with unrestricted database write access can recompute the chain from the point of edit onward and leave it internally consistent. Closing this requires publishing chain heads to independent storage.
  • The signing key resides in a file. It can therefore be copied, which materially weakens any non-repudiation claim. Production deployment should hold the key inside an HSM or cloud KMS from which it cannot be exported.
  • Trust in a certificate authority is assumed. If a configured CA mis-issues a certificate, the result is reported as trusted. This is inherent to PKI rather than a defect of this implementation.
  • A valid signature does not imply truthful content. It establishes only that the document is unchanged since an identified party signed it.

12 Conclusion

Key findings

  • Cryptographic integrity verification is decisive where visual inspection is useless. A length-preserving single-figure alteration produced a file indistinguishable from the original to a human reader and to a PDF viewer, yet was detected with certainty by digest comparison over the signed byte range.
  • Separating independent checks preserves diagnostic information. Reporting integrity, signature validity, certificate status, chain trust, revocation and timestamp as six distinct results allowed a tampered document to be correctly described as having modified content and a valid certificate — a distinction that a single boolean verdict necessarily loses.
  • Honest reporting of uncertainty is an implementable engineering property. By modelling "not checked" and "not available" as first-class states in the domain model, the API contract and the frontend type system, absence of evidence is structurally prevented from being rendered as evidence of safety.
  • Trust must originate outside the artefact being verified. Validating a signature against the certificate chain embedded in the same document is circular; the design therefore derives trust exclusively from externally configured anchors.

Overall outcome

The project delivers a working platform of 83 passing automated tests across signing, verification, authorisation, audit integrity and adversarial security scenarios. It demonstrates that the difference between a trustworthy and an untrustworthy document is not a matter of appearance but of arithmetic — and, equally, that a system's credibility depends on declaring what it has not verified as clearly as what it has.
